Incremental impact By failure cause

Gross recovery cannot separate money the agent won from money that would have come back anyway — some failed charges recover on their own when a customer tops up or an issuer stops declining. A randomised slice of cases is therefore held out: detected and diagnosed like any other, then never intervened on. The gap between the arms is the agent's effect.

A table in which every row is a win is a table nobody should believe. Arm counts are on every row: a lift over eight cases and a lift over eight hundred are not the same claim.

Are the agent’s own priors any good?

P_RECOVER_PRIOR decides which interventions fire and which cases go to a person. Until now it had never been checked against a single realised outcome — a number that decides where money goes and has never been scored is an assumption wearing a measurement’s clothes.

What the agent declined to do

Not every failure is equally recoverable. An expired card does not un-expire; an empty account often refills by payday.

Pipeline Guardrails Decision policy Model boundary

Every number here is a row count in the database. Two gates sit inside the loop — one before a decision is made, one immediately before it executes — because state can change in between.

Every invariant below is enforced in a module that imports neither the policy table nor the model — so a wrong policy cell cannot route around them and no model output can reach them. They run before a decision and again before execution. The counts are live.

Dispatch fencing

Every invariant above re-reads the case — our record of the world, exactly as stale as the last webhook that happened to arrive. These three fences re-read the world itself, because between deciding and acting the customer may already have paid. A fence degrades, it never raises: when it cannot reach the truth it records unverified and lets the dispatch through, so “we did not check” is never mistaken for “we checked and it was fine.”

The intervention comes from a static table indexed by (failure cause, attempt number). It is total — every cell filled — so the lookup cannot fall through to a default, and every decision records the exact cell it came from.

Open the subscribe demo

The two panels below are the raw developer shortcuts the subscribe demo is built on top of — useful for poking at one specific rule directly.

Developer shortcut — real checkout

  1. Click "Pay ₹499" — creates a real Order and opens a pipeline tab that watches its case update live.
  2. In checkout, fail the payment any way it lets you. Netbanking's mock failure ("declined by the bank") maps to a known rule; Wallet's generic "temporary issue" does not, and Sahara will honestly stop rather than guess at it.
  3. The pipeline tab updates within ~1s of each webhook. Its "Fast-forward to next action" button skips real wall-clock delays instead of waiting hours between attempts.

Developer shortcut — inject a category directly

Razorpay's test-mode checkout only offers a few fixed decline reasons, so it can't reliably reach every rule. This pushes the same shape of payment.failed body through intake() — the identical function a live webhook calls, with source="synthetic" the only difference — so you can watch any of the six diagnosed categories run the pipeline live, on demand.
